# 同期問題

## 同期問題とは

PvPでは，2つのクライアントがそれぞれ独立に試合を計算しており，サーバーは片方が送ってきたメッセージをもう片方へ渡すだけで，試合そのものは計算していません．そのため，行動した側が計算した結果と，受け取った側が再計算した結果が食い違うと，そこから先の盤面が別物となり，同期ずれが起こります．

例えば，次のようになります．

- コストを払って出したカードが，相手の画面に現れない
- フォロワーが片方の画面では破壊されたが，もう片方では生き残っている
- 相手のリーダーを攻撃しても，自分の方では相手のリーダーの体力が減っているが，相手の視点では攻撃すらされていない
- 体力やPPの数字が合わない

なお，実際にはエラーなどがゲーム画面には出ず，どこかのタイミングでプレイヤーが気付くというような形が多いため目視だと切り分けが難しいことがあります．

以降，メッセージを渡す側のサーバーを中継，そのメッセージを出したクライアントを行動側，受け取るクライアントを受け手として記述します．

## 原因

PvPでは，クライアントは相手のデッキを持っていません．相手のデッキを入れる口はありますが，呼ぶのはリプレイローダーだけで，対戦中は通りません (`SetOppoDeck`)．そのため対戦中は，相手のデッキとしてダミーカードが40枚返ります．

相手のカードがどれか，そのコスト・ステータス・カウンタ・種族が何であったかは，元のサーバーが試合を計算した上で書いて送っている値で，中継は試合を計算していないので，これを書くことができません．

それにより，以下ように必要な情報が通信に載らないことがあります:

- コストカット系 (例えば`NetworkSkill_cost_change.IsSend`) は，コストを変更した対象が手札にある限り常にfalseを返す
- 行動側の解決記録 (`orderList`) は，607k行のクライアント全体でどこも受け取らない (書き込みが1箇所あるだけ)
- 受信側が受け取れるフィールドのうち約18個は，どの綴りでも書き手が存在しない

コストを伝えないことは中立ではありません．受け手は値を明示されたときだけ補正を入れる作りなので，何も言わなければ基本コストで課金します．自分でPPを引き算しているため，やがてPP不足でプレイ全体を拒否し，攻撃の可否判定なども連鎖して落ちます．ログには`IsPlayCard PPover`や`ConductError`が残ります．

### CP対戦がずれない理由

CP対戦は通信対戦とは別の型で組まれており，受信経路には構造的に到達できません (`BattleType.Practice`)．そもそもメッセージを出さないので，PvPの実装が参考にできる出力もありません．

一方で，CP対戦の操作記録は両者のプレイを実効コスト付きで書き出します (`SingleBattleOperationRecorder`)．クライアントを改変せず，対戦相手も用意せずに，中継が推測しているコストの正解値を取得できます．

## 方針

クライアントのバトルエンジンをヘッドレスで並走させたものを，クライアント1つにつき1基，サーバーが両方持ちます．以降これをミラーと呼びます (コード上も`MirrorPair` / `ShadowMirror`)．中継が値を組み立てる必要がなくなり，相手に伝える値はそのクライアント側のミラーから読み出すだけで済みます．

1基では足りない理由:

- 自分の効果でしか進まない2本目の乱数があり，共有カウンタを触らずに引かれる (`_stableRandomOnlySelf`)．構造として1クライアントに1本
- `spin`は「行動側の消費 − その受け手が再シミュレートで消費した数」なので，受け手の側を再現しないと出せない
- 受信側の検査は相手側の盤面を決め打ちで見るため，向きの合ったミラーでしか意味を持たない

### `SetDeckMirror`を切っている理由

これを立てるとマリガン終了の扱いになり，`ShadowReconciler`がデッキへ戻す経路が，実際には引いていないドローとして扱われます．両者が排他になっているだけで，ミラー側が壊れているわけではなく，サーバーが配る側になれば`ShadowReconciler`は不要になって有効にできます．

## 到達点の定義

公式サーバーは動いていないので突き合わせる記録がありませんが，検査の仕組みはクライアントに同梱されています．受信メッセージを受け手の盤面に照らして，行動カードの在否・攻撃の可否・プレイしたカードが手札にあるかを見る検査です (`OperateReceiveChecker`)．Cygames自身による同期ずれの定義にあたり，失敗するとそのメッセージが捨てられ，ログに`ConductError`が残ります．

達成条件は5つの数値がゼロになることです．

| | 指標 |
| --- | --- |
| O1 | ConductErrorの発生数 |
| O2 | 2基のミラーの盤面差分 (乱数カーソルを含む) |
| O3 | 解決できないpublish count (現状のキャプチャで3/5) |
| O4 | 683組の (オペコード, タイミング) のうち未通過のもの |
| O5 | 未処理のvfxキュー |

## 残る限界

- サーバーが決める値: `spin`，相手に伝えるカードの情報，条件への回答は，クライアントが読むだけで一度も書きません．形式は決まっていますが，何を入れるかはどこにも記録されていません．ここは再現ではなく設計になります
- エンジンは607k行から，Cygamesが使っていないコンパイラで組み直した再構築物です．IL差分で違いの範囲は絞れますが，ゼロにはできません．ビルドを固定してハッシュを配り，2つのホストが気づかないまま別物にならないようにします
- ガード付きコンストラクタはnullアセットで本体ごと飛ばすので，その中に状態変更が紛れていればミラー側も飛ばします．例外を追っても出てきません

## 実装

**どちらがownerか**: 接続順では決まりません．クライアントは試合ごとにソケットを張り直すため2戦目以降は再接続の競争になり，取り違えるとデッキも戦績も入れ替わります．部屋を作ったメッセージの送信者がowner，入室が訪問者なので，どちらか一方から両方が決まります (`RoomCreate` / `RoomEntry`)．

**モードフラグ**: 通信対戦であることをエンジンに伝えないと，ソロ戦の分岐を通って，どちらのクライアントも引いていないローカル乱数を引きます (`GameMgr.IsNetworkBattle`ほか)．

**盤面の突き合わせ**: 行動側のターン終了と受け手の応答の対 (以降，境界と呼びます) について，各クライアントが送ってくる盤面のハッシュ3つ組を突き合わせます (`ConsistencyWatch`)．食い違えばどの組が壊れたかをログに出すだけで，まだ何もしません．

同梱のキャプチャは境界9-11で破綻します．気づかれないまま同期ずれを起こした試合で，`ShadowCostFidelityTests`が値を確かめているプレイは破綻後の盤面に乗っています．そのため異常の検知には使えても，正解の基準にはなりません．墓地の枚数は独立した信号に見えますが，2つのターン終了は別のターンに出るのでそのままでは比べられません．ハッシュの1つ目が墓地をまとめているため，ずれはそちらに出ます．

**同期ずれで試合を終わらせる**: 終了メッセージに`endType=2`を載せると，クライアント内部の無効試合の経路を通って900/901が返ります．中継側はこれを既に両者無効試合として扱います．`OPENVERSE_DESYNC`で`warn` (既定) と`stop`を切り替えます．`stop`でも，1回は遅れて届いただけのことがあるので，連続2境界壊れるまでは試合を終わらせません．

**切断の検知**: 回線が切れてもTCPソケットはすぐ閉じないため，切断の通知は数分遅れるか永久に来ません．受信のたびに最終受信時刻を更新し，20秒途絶えたら切断決着へ落とすので，クライアント自身が試合を諦める95秒には間に合います．

**試合間の持ち越し**: 部屋は複数の試合を持つので，ミラーの状態は試合ごとにクリアし，どの終了経路からも必ず解放する必要があります．どちらも欠けていたため，2戦目以降は前の試合の盤面で答えていました．

**コンテキスト分離**: ミラー1基につき専用のアセンブリ読み込みコンテキストを持たせます (`EngineContext`)．共有していても両方それらしい盤面を出すので，盤面の出力では検出できず，判定は型の同一性で行うしかありません．

**ConductErrorの計測**: クライアントは自分のログをサーバーへ送っており，そこに`ConductError`とその理由が入っています．サーバーは既に受け取っていて，リクエスト本文の中に埋もれていただけだったので，抜き出してカウンタ付きでログに出します．

実測の基準値は，友人との6戦で30件です．

| 理由 | 件数 |
| --- | --- |
| 行動カードが見つからない | 11 |
| プレイしたカードが手札にない | 10 |
| プレイ対象が見つからない | 4 |
| スキル選択の検査に失敗 | 3 |
| 理由の記録なし | 2 |

ログに残ったカード`112821010` `125811030` `720831010`は，同じ試合で中継がコストを伝えられなかったカードと一致します．原因の節で書いた経路が実データで繋がりました．

**2基の構成**: それぞれ自分の40枚を自分側に，ダミー40枚を相手側に置きます (`MirrorPair`)．クライアントが実際に持っている盤面と同じ形です．同じメッセージが片方には自分の行動，もう片方には相手の行動として入るので，取り違えると動いているように見えて中身が逆になります．テストで固定してあります．

**ミラーから値を読む**: ミラーのカードオブジェクトから，カードID・コスト・攻撃力・体力・スペルブースト回数・詠唱・種族・クラスを読みます (`ShadowMatch.Project`)．隠しゾーンへの質問も，そのゾーンを持っている側へ回します．コストは加算・設定・半減の各修正を適用した後の値で，受け手には計算する手段がありません．

中継が値を出せなかったときだけ使います．採用の条件は，同じインデックスにあるカードのIDが一致し，値が0以上かつ基本コスト以下であることです．外れたら盤面が食い違っている合図なので採りません．固定使用コストとアクセラレートの価格は，読めても伝えません．受信側はこの2つの大小関係でアクセラレートを判定するため，固定すると全てのアクセラレートが弾かれます．

**`spin`**: 受け手は行動側の操作をダミー40枚に対して再シミュレートするので，乱数のカーソルが行動側より手前で止まります．`spin`はその差で，受け手はその回数だけ乱数を捨てて追いつきますが，前進しかできないため差が負になる場合は送りません．

**部屋ごとに持たせる**: プロセス全体で1組だったため，2部屋が同時に走ると互いの質問に答えていたので，部屋ごとに持たせてプールから貸し出します (`MirrorPool`)．上限 (`OPENVERSE_ENGINE_PAIRS`，既定2) を超えた部屋には渡さず，ミラー無しで中継します．盤面を共有させるより安全なためです．

**送信前の拒否検査**: 受け手側の盤面に流した直後に，そのクライアントが落とすかどうかを読み，落とされるならログに出します．送信自体は止めません．行動側は既に手元で確定しているので，送らなければ片側にだけ盤面が残る状態が続き，落とされるより悪くなります．

**操作から動かす**: 受信経路ではなく，クライアントが自分の操作を流すのと同じ入口からミラーを動かします (`ShadowMatch.PlayByIntent`)．AIが使う入口で対戦種別の分岐がないため，受信経路より通りやすくなります．

ただし有効にすると`ShadowCostFidelityTests`が2から6に外れ，スペルブーストを16回のうち13回しか数えていません．そのため`OPENVERSE_ENGINE_INTENT`で明示的に有効化する形にし，既定はoffです．失敗時は受信経路に落ちるので今より悪くはなりませんが，正しくなる保証もありません．残っている未解決点はここです．

未検証ですが，この経路はプレイ前の盤面補正を通らず，成功すると行動側の受信処理ごと飛ばします．デッキから手札へ移す処理が抜けるため，通信が手札に置いたカードがデッキに残ったままだとスペルブーストされません．補正を先に呼べば決着しますが，測ってから判断すべきところです．

### コピーされたクライアントのviewer_id

インストールをコピーするとキャッシュ済みのviewer_idも一緒に移り，両クライアントが同じ値を名乗ります．席の判定だけの問題ではありません．クライアントは自分のidをサーバーから渡された値として持ち，受信側は宛先つきの値を宛先が自分でなければ捨てます．`spin`もこの形式なので，同じidだと常に捨てられます．

対策は2つ入れました．

- 席の判定を接続元IPで行う．APIがリクエストの送信元を記録し，Battle側がソケットの接続元と突き合わせる．クライアントが選べない唯一の値になる．同一NATの背後に2人居る場合はIPも同じになるので，そのときはviewer_idのpin，さらに接続順へ落ちる
- クライアントへ渡すidを席から導く．両ソケットが同じidを名乗る場合，ownerはそのまま，visitorを1つずらす

### 葬送とリアニメイト

カードIDを付けるのはフィールドに着いたものだけで，葬送は手札から墓地なので対象外でした．どのカードかを伝えられなかった結果，受け手は自分のダミーデッキから埋め，葬送したフォロワーがゴブリンになります．

墓地と消滅は両者が見られるゾーンでカードIDを伝えても情報が漏れないため，到着先の判定をフィールド・墓地・消滅に広げました．手札への到着は引きが漏れるので従来通り除外し，手札からフィールドへのプレイは別の経路の担当なので触りません．

リアニメイトが怪しく見えたのはこの二次被害です．墓地に無名で入ったカードはインデックスとカードIDの対応表に載らないため，後からそこを蘇生してもカードIDを伝えられません．

### どのカードを伝えるかの基準

シュヴァリエ・マグナ (`119241030`) は結晶1で場に出すと，事前に指揮官・カードを融合していれば，相手のフォロワーすべてをバニラにします (攻撃力と体力はそのまま)．

伝えるのはプレイしたカードだけなので受け手側の素材はダミーのまま残り，種族が付いていないため指揮官を要求する融合の条件に合わず，素材が積まれません．融合していない扱いになって効果が発動せず，相手のフォロワーは能力を保ったままなので，以降の攻撃が拒否されます．

受信側の検査には融合の分岐が無いため，融合のメッセージ自体は検査を通り，エラーが出ないまま盤面だけが食い違うので気づかれませんでした．

融合素材は専用のゾーンへ行き，移動の記録すら出さないので，到着先を見る限り届きません．到着先で決める判定はそのまま残し，そのメッセージが受け手に引かせるインデックスを全て伝える判定を足しました．これは融合だけでなく，隠れたカードの属性を読む分岐すべてに効きます．なお相手に伝えられるのはカードのデータモデルが持つ項目だけで，融合状態は運べません．

### スペルブースト回数はコスト減とは限らない

通信上のスペルブースト回数は，スペルを唱えたときに加算される汎用のカウンタです．スペルブーストの能力を持たないカードにも乗るのが正常で，マスタでこの回数を読むスキルは，コスト減が100件に対し，ダメージ・トークン生成・回復・スタッツが54件あります．

これを取り違えて，中継は回数の乗ったカードを値段の言えないカードとして扱い，実測済みのコスト差分ごと捨てていました．実戦では戦地への呼び出しが2枚に-1を配り，片方だけが無関係なスペルブーストを受けたため，その1枚だけ基本コストで伝わってPP不足で捨てられました．同じメッセージで引かれたもう1枚は正しく伝わっており，差はスペルブーストの有無だけです．

割引を持たないカードと，割引はあるが割引幅を読めないカードを区別するようにして，値段を出さないのは後者だけに絞りました．該当は2枚です．

この回数をコスト以外に使う54件は，中継が何もモデル化していません．行動側が結果を具体値で送るので普段は問題になりませんが，受け手が自分のスペルブースト回数を誤って数えていればダメージや枚数が食い違います．

### プレースホルダに使うカードID

クライアントがダミーとして使うのは，効果を持たないゴブリン (`100011010`) です．中継とミラーは`100111010`を使っていましたが，これは実在するウォーターフェアリーで，ラストワードでフェアリーを手札に加えます．体力も1違います (1/1と1/2)．

ミラーの相手デッキ40枚が全てこれだったため，ダミーが1体死ぬたびにミラー側だけ手札が増えていました．中継はその盤面から値を読みます．「これは伝えない」という印としても実在カードと衝突しており，エルフがウォーターフェアリーを出すとそのカードIDが消されていました．

同じ値の定数が3箇所にあったことが取り違えを見えなくしていたので，1つにまとめました．

### トークンのカードIDは伝えるしかない

相手のカードを伝える情報はヘッドレスでは扱えずエラーになるので，ミラーには渡していませんでした．デッキのカードはインデックスで引けますが，試合中に生成されたカードはデッキ枚数を超えるインデックスを持ち，カードIDがそこにしかありません．落とすと受け手側はそのカードを置けず，以降そのインデックスを指すメッセージが全て落ちます．

クライアントが読まないキー名でミラー側まで運び，盤面に無いインデックスだけエンジン自身のトークン生成経路で作るようにしました．ビューを必要としない経路なのでヘッドレスでも通ります．同梱キャプチャの脱落が72行中2行から0行になりました．
